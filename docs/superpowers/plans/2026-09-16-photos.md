# Photos Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A small photo library: photos live on the drive attached to the Pi, the newest few show on the home page, a Photos page shows them all, and photos can be added (and removed) through the site.

**Architecture:** The music pattern, with one addition. Disk is the source of truth: `PHOTOS_DIR` is walked by `scan-photos` into a rebuildable `photo` table keyed by path. Unlike music, the site also *writes* to the drive: an upload saves the file under `PHOTOS_DIR/YYYY/MM/` and indexes it in the same request; a delete removes the file and the row. Thumbnails are made with Pillow on first request and cached in a dot-directory the scanner ignores. `caption` is the one curated field and lives only in the table; rows are updated in place so captions survive rescans.

**Tech Stack:** as before, plus `Pillow` (aarch64 wheels exist for the Pi).

**STATUS, 2026-09-16: Tasks 1-5 done and the deploy notes written; the manual check in Task 6 is Greg's.** Backend 478 unit tests, frontend 171. ## Decisions

- **Two image sizes, not arbitrary.** `w=400` for grids, `w=1200` for the lightbox. Anything else is a 400. Arbitrary widths would let one page fill the drive with cache files.
- **JPEG, PNG, WebP, GIF in; HEIC out with a clear message.** iOS Safari converts HEIC to JPEG for web uploads on its own, so rejecting HEIC costs nothing in practice and avoids `libheif` on the Pi.
- **Upload limit 25 MB per file**, and the file is opened with Pillow before it is kept: a renamed `.exe` is refused.
- **EXIF is honoured.** Orientation is applied when making thumbnails and when reading width/height; `DateTimeOriginal` becomes `taken_at`, falling back to the file's mtime. Newest-first ordering uses `taken_at`, so a photo from last summer uploaded today files under last summer.
- **Upload names are ours.** `PHOTOS_DIR/YYYY/MM/YYYYMMDD-HHMMSS-<6 hex>.<ext>` from `taken_at`. The client's filename is never used as a path.
- **Delete is real** and asks first in the UI. It removes the file, its cached thumbnails and the row, in that order, only if the path resolves inside `PHOTOS_DIR`.
- **The home page shows the newest six** as polaroids: white frame, the photo, the caption beneath in Fraunces italic, each tilted a degree or two alternately. It is the one place the site gets to be playful, and it is for Liv.
- **No albums, no search, no favourites.** Recorded below; all additive.

## Schema

```sql
CREATE TABLE IF NOT EXISTS photo (
    id INT AUTO_INCREMENT PRIMARY KEY,
    path VARCHAR(768) NOT NULL UNIQUE,
    taken_at DATETIME NOT NULL,
    width INT NOT NULL,
    height INT NOT NULL,
    format VARCHAR(8) NOT NULL,
    size_bytes BIGINT NOT NULL,
    mtime_ns BIGINT NOT NULL,
    caption VARCHAR(255),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    INDEX photo_recent (taken_at, id)
)
```

`path` as in `track` (768, full unique index). `taken_at` is never null: mtime is the fallback. `photo_recent` serves `ORDER BY taken_at DESC, id DESC` the way `track_listing` serves the music sort, with `id` listed explicitly for the same reason.

## Configuration

| Variable | Required | Meaning |
| --- | --- | --- |
| `PHOTOS_DIR` | yes, for photos | Absolute path to the photos root. A subdirectory of the mount, as with music. |
| `PHOTOS_THUMBS_DIR` | no | Thumbnail cache. Default `PHOTOS_DIR/.thumbnails`. |

## Endpoints, under `/api/photos`

| Method | Path | Does |
| --- | --- | --- |
| GET | `/photos?limit=&offset=` | `{photos, total, limit, offset}` newest first. `limit` default 60, max 200. |
| GET | `/photos/<id>` | One photo: `{id, taken_at, width, height, format, size_bytes, caption}`. Never `path`. |
| PUT | `/photos/<id>` | `{caption}` → 204. Empty string clears it. |
| DELETE | `/photos/<id>` | Removes file, thumbnails, row → 204. |
| GET | `/photos/<id>/thumb?w=400\|1200` | JPEG, EXIF-corrected, cached, `Cache-Control: public, max-age=31536000` (the id never changes meaning). |
| GET | `/photos/<id>/file` | The original, with its real mimetype. |
| POST | `/photos` | multipart, field `files` (repeatable). → 201 `{added: [photo...], rejected: [{name, reason}]}`. One bad file does not fail the others. |

## Reuse, not duplication

- `music/scanner.find_audio_files` becomes `find_files(root, extensions, on_error)` with `find_audio_files` a one-line wrapper. The photo scanner calls `find_files`.
- `_refuse_mass_removal` gains a `table` argument for its messages and moves to a shared `library/rails.py` with `ScanAborted`, `REMOVAL_LIMIT`, `REMOVAL_FLOOR`. Music imports them from there.
- `music/config.resolve_inside_music_dir` is rebuilt on a general `resolve_inside(root, path)`; photos use it with `photos_dir()`.

The music tests must stay green through each refactor before the photo code that needs it is written.
