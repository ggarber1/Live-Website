# Music Library UI (Phase 1, final task) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The "minimal browse-and-play UI" that the Phase 1 spec lists in scope and the backend plan never built. Search the library, page through it, click a track, it plays, seeking works, the next track follows.

**Architecture:** A Vite + React + TypeScript single-page app in `frontend/`. It talks to the existing HTTP API and nothing else. In development it runs on Vite's dev server against `localhost:5000` (already a CORS default). In production Flask serves the built `frontend/dist` from the same origin, so the Pi runs one process and CORS is irrelevant there.

**Tech Stack:** Node 23 / npm 10, Vite, React 19, TypeScript, Vitest + React Testing Library + jsdom. No UI framework, no router, no state library. Plain CSS in one file.

Spec: `docs/superpowers/specs/2026-09-09-media-library-design.md`
Backend plan: `docs/superpowers/plans/2026-09-13-music-library.md`

## Decisions, so they are not re-litigated

- **One page, no router.** Phase 1 is a list and a player. Playlists, favourites and cinema come later and can add a router then.
- **Flask serves the build.** The spec's Phase 3 diagram already puts Flask behind Caddy at `/`; serving `dist/` from Flask now keeps deployment a `git pull && npm run build && systemctl restart`. A second static server is a second thing to break on the Pi.
- **The API base URL is `VITE_API_URL`, defaulting to `''`.** Empty means same-origin, which is production. Development sets it to `http://localhost:5000` in `frontend/.env.development`, which is committed because it holds no secrets.
- **The player is one `<audio>` element that outlives the list.** Changing pages or searching must not stop playback. That is the whole reason the player is not inside the list component.
- **Auto-advance stays within the page the track was clicked from.** The player holds its own copy of the queue at click time. Searching or paging afterwards does not change what plays next.
- **No debounce library.** A 300 ms `setTimeout` in an effect is enough and is easy to test with fake timers.

## What the API gives you

From `backend/music/music.py`, unchanged by this plan:

| Call | Returns |
| --- | --- |
| `GET /music/tracks?q=&limit=&offset=` | `{tracks: Track[], total, limit, offset}`; `limit` default 50, max 200; 400 on bad input |
| `GET /music/tracks/<id>` | one `Track` or 404 |
| `GET /music/tracks/<id>/stream` | audio bytes, byte ranges supported, real mimetype |

`Track` is `{id, title, artist, album, track_no, duration_seconds, format, size_bytes, created_at}`. `artist`, `album`, `track_no` and `duration_seconds` can be `null`. There is never a `path`.

## File structure

**Create (all under `frontend/`):**

| File | Responsibility |
| --- | --- |
| `package.json`, `vite.config.ts`, `tsconfig.json`, `index.html` | Scaffold. |
| `.env.development` | `VITE_API_URL=http://localhost:5000`. |
| `src/main.tsx` | Mounts `<App/>`. |
| `src/api.ts` | `listTracks`, `streamUrl`, the `Track` type. The only file that knows URLs. |
| `src/format.ts` | `formatDuration(seconds)` and `describe(track)` for the artist/album line. Pure. |
| `src/App.tsx` | Owns `query`, `offset`, the fetched page, and the play queue. Renders the three components below. |
| `src/SearchBox.tsx` | Controlled input, debounced `onChange`. |
| `src/TrackList.tsx` | The table, the pager, and which row is playing. |
| `src/Player.tsx` | The `<audio>` element, now-playing text, auto-advance. |
| `src/styles.css` | Everything visual. |
| `src/*.test.tsx`, `src/*.test.ts` | One test file per module above. |

**Modify:** `backend/app.py` (serve `dist/`), `backend/tests/test_app.py` or a new `backend/tests/test_static.py` (fallback behaviour), `deploy/README.md` (build step), `.gitignore` (`frontend/dist/`).

### Task 2: API client and formatting helpers

**Files:** `src/api.ts`, `src/format.ts`, and their tests.

- [ ] **Step 1: Write the failing tests**

`src/api.test.ts`, with `globalThis.fetch` replaced by `vi.fn()`:

- `listTracks({q: 'tone', offset: 50})` calls `<base>/music/tracks?q=tone&limit=50&offset=50` and returns the parsed body.
- `listTracks({})` omits `q` from the query string entirely; the backend treats blank and absent alike, but the URL should not carry noise.
- A non-2xx response rejects with an error whose message includes the body's `error` field. This is the failure case: the backend's 400 for a bad `limit` must surface, not render as an empty library.
- `streamUrl(7)` is `<base>/music/tracks/7/stream`.

`src/format.test.ts`:

- `formatDuration(0)` → `0:00`, `formatDuration(65)` → `1:05`, `formatDuration(3725)` → `1:02:05`, `formatDuration(null)` → `''`.
- `describe(track)` joins artist and album with ` — ` and drops whichever is null; both null gives `''`.

- [ ] **Step 2: Run them, watch them fail on the missing modules**

- [ ] **Step 3: Implement**

`api.ts` reads `import.meta.env.VITE_API_URL ?? ''` once at module level. `listTracks` builds the query with `URLSearchParams`, sets `limit=50`, skips empty `q`. On `!res.ok` it reads the JSON body defensively (a proxy could return HTML) and throws `new Error(body.error ?? res.statusText)`.

### Task 4: Player

**Files:** `src/Player.tsx`, `src/Player.test.tsx`.

jsdom does not implement media playback: `HTMLMediaElement.prototype.play` throws "not implemented". Stub `play` and `pause` with `vi.fn()` in `setup.ts`, resolving `play` to a promise. The tests below are about wiring, not audio.

- [ ] **Step 1: Write the failing tests**

- With no track it renders an empty bar and an `<audio>` with no `src`.
- Given `track` it sets `src` to `streamUrl(track.id)`, shows the title and `describe()` line, and calls `play()`.
- Changing `track` to a different id changes `src` and calls `play()` again.
- Re-rendering with the same track does not reset `src`. This is the guard against the list re-render restarting playback every time the user types in the search box.
- Firing `ended` on the `<audio>` calls `onEnded()`.

- [ ] **Step 2: Fail, implement, pass**

`Player` takes `{track, onEnded}`. `<audio controls>` is rendered once and its `src` set in an effect keyed on `track?.id`. The browser handles seeking itself; that is what the backend's `206` support is for, and it was verified by hand in the backend plan's Task 13.

### Task 5: Wire it together in App

**Files:** `src/App.tsx`, `src/App.test.tsx`, `src/styles.css`.

- [ ] **Step 1: Write the failing tests**

`App.test.tsx` mocks `./api` with `vi.mock`:

- On mount it calls `listTracks` with an empty query and renders the result.
- Typing in the search box, after the debounce, calls `listTracks` with `q` and `offset: 0`. Offset must reset on a new search or a user on page 3 sees an empty page 3 of a new result set.
- Clicking Next calls `listTracks` with `offset: 50`.
- Clicking a row makes the player show that title.
- Firing `ended` on the audio plays the next track in the list as it was when the click happened. Set this up by clicking the first of three tracks, then searching so the list changes, then firing `ended`: the player must show track two of the original three, not the first of the new list.
- Firing `ended` on the last track leaves the player on that track, stopped, rather than looping.
- When `listTracks` rejects, the error message is shown and the previous list is left in place.

- [ ] **Step 2: Fail, implement, pass**

`App` holds `query`, `offset`, `page` (the last successful response), `error`, and `queue: {tracks, index} | null`. Clicking a row sets `queue` to `{tracks: page.tracks, index}`. `onEnded` advances `index` if there is a next entry. The player is passed `queue?.tracks[queue.index]`.

### Task 6: Flask serves the build

**Files:** `backend/app.py`, `backend/tests/test_static.py`, `deploy/README.md`.

The API and the SPA share one origin in production. Flask serves `/` and any file that exists under `frontend/dist/`. **No `index.html` fallback**: there is no router, so no deep links exist, and a catch-all would turn every mistyped API path into a 200 HTML page and break the existing JSON-404 contract (`test_http_errors_still_use_their_own_handler`). Add the fallback when a router arrives, and scope it then.

- [ ] **Step 1: Write the failing tests**

`backend/tests/test_static.py`, using a `tmp_path` dist directory and `monkeypatch.setattr(app_module, 'DIST_DIR', ...)`:

- `GET /` returns the `index.html` contents with `text/html`.
- `GET /assets/app.js` returns that file.
- `GET /music/track` (a typo) is a JSON 404, not the index page.
- `GET /music/tracks` still reaches the API. This is the failure case worth having: a rule registered too greedily shadows every blueprint.
- `GET /..%2F..%2Fapp.py` does not leak source.
- With no dist directory, `GET /` returns a 404 JSON body saying the frontend has not been built, rather than a traceback.

The existing `howdy` route on `/` goes away; check `test_schema.py`'s request list and any other test that hits `/` and update them in the same change.

- [ ] **Step 2: Fail, implement, pass**

`DIST_DIR` next to `app.py`, resolved to `../frontend/dist`. One view on `@app.route('/')` and `@app.route('/<path:path>')` with `path='index.html'` as the default, returning `send_from_directory(DIST_DIR, path)`; missing files and traversal are already 404 there. Flask matches blueprint rules before the converter-based rule because they are more specific, but the test above is what proves it.

- [ ] **Step 3: Deploy notes**

Add to `deploy/README.md` after the configuration section: install Node on the Pi (`apt install nodejs npm` is adequate), then `cd frontend && npm ci && npm run build`. Note that a rebuild is needed after every frontend change and that `CORS_ORIGINS` is now only relevant for development.
